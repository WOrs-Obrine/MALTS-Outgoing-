# 01 · 安装与启动：从零到「她回你一句」

目标只有一个：**先跑通最小闭环——一条私聊、她回一句**。之后再叠功能。
顺序别乱，原因在每一节末尾。

---

## 0. 前置

- Windows 10/11，常开；最好有断电自启
- [DeepSeek Harness Desktop](https://github.com/deepseek-ai)（下称 DSH Desktop）装好，模型 key 可用
- 一个**小号 QQ**——别用主号，掉线、风控、封号风险都让它承担
- [NapCat](https://napneko.github.io/) 或其他 OneBot v11 实现

> **为什么一定要小号**：协议端不是官方客户端，腾讯的行为检测是真实存在的。用小号是对你自己负责，不是怂。

---

## 1. NapCat 登录小号、开正向 WS

1. 装 NapCat（Desktop 版最省事），用小号扫码登录
2. 网络配置里新建 **WebSocket 服务端**（正向 WS），端口比如 `3001`
3. 设一个 access token（后面插件要填）
4. 验证：能连上 `ws://127.0.0.1:3001` 就算通

**为什么用正向 WS，而不是插件去连 NapCat 的 HTTP**：WS 是长连接、事件推送，一条消息到就是一条事件，天然贴合「收到消息 → 唤醒 agent」这个模型；HTTP 要轮询，延迟与成本都更差。

**顺手开 HTTP 服务**（比如 `3000`）：调试时 `get_group_msg_history`、`get_login_info` 很好用，面板也会用到它。

---

## 2. 装 DSH Desktop 与 `dsh-onebot-qq`

1. DSH Desktop 能正常开一个会话、能读写文件
2. 插件市场装 **`dsh-onebot-qq`**（本仓库以 `0.9.4` 为基准；大版本升级后 API 可能变，见 04 的「版本漂移」）
3. 打开 `profiles/web/cordis.patch.yml` 填空：

```yaml
dsh-onebot:
  wsUrl: ws://127.0.0.1:3001
  accessToken: "你的 token"
  botQQ: 1000000001          # 小号
  ownerQQ: 1000000002        # 你自己——「主人」权限只认这个号
  adminUsers: ["1000000002"]
  dmPolicy: allowlist        # 私聊只回名单里的人
  dmFriendsOnly: true
  requireMention: true       # 群里 @ 或叫名字才回
  persona: "D:/my-bot/persona/my-fish.md"
```

4. 重启宿主，日志里应出现 `bridge ready (N resumed chat(s))`
5. 私聊小号发一句，能收到回复 → **最小可用版本成了**

**为什么 `ownerQQ` 要单独一个字段**：后面所有危险能力（改文件、开发者模式、敏感功能）都靠「是不是这个号」来放行。把它做成配置而不是硬编码，是为了换号时不用改代码。

**为什么默认 `requireMention: true`**：群聊里每条消息都回，Token 会以肉眼可见的速度烧。@ 才回，是把「唤醒」的决定权交给人。

**为什么 `allowlist` 而不是全回**：陌生人私聊会带来两类问题——安全（提示词注入、骗工具）和成本（被刷）。先只回名单，确定要放开再加。

---

## 3. 挂人设

1. 把人设 Markdown 放进你的「提示词库」目录，比如 `提示词库/我的鱼.md`
2. 配置里 `persona` 指过去
3. **人设每回合现读**：改完保存即生效，不用重启
4. 验证：她会自称人设里的名字、语气变了

**为什么是「现读文件」而不是写进代码**：调人设是最高频的操作，一天可能改十次。写进代码就要重启，重启就会打断正在进行的回合。文件是最低成本的「热更新」。

写法见 [`02-人设怎么写.md`](02-人设怎么写.md)。

## 4. 加旁听侧车（可选，但强烈建议）

侧车是一个**独立本地 Node 进程**，用 WS 旁听，**不占上下文、不花 token**：

- 算印象/好感、激素、养成数值
- 定时写「状态卡」，供人设每回合读取
- 主动找人（戳一戳、主动私聊、固定群冒泡）
- 维护记忆、写日记、统计用量、清理旧会话

骨架在 `侧车/侧车骨架.mjs`，行为约定见 [`03-系统咬合.md`](03-系统咬合.md)。

**为什么要独立进程而不是塞进插件**：
1. 插件跑在宿主进程里，崩了会拖着 agent 一起崩；
2. 侧车要能独立重启（改完立刻生效），不该每次都重启宿主；
3. 它本来就不需要模型能力，跟插件绑在一起只会互相拖累。

启动：`cmd` 一行拉起 + Windows 计划任务（开机自启 + 5 分钟看护）。
**务必保证单实例**——两个侧车同时写同一个 JSON，会互相覆盖（见 04）。

## 5. 补丁守护（可选，但一旦开始改插件源码就必须有）

改过 `node_modules` 里插件源码的人都会遇到同一件事：**宿主一升级，你的补丁就被覆盖了**，而且往往是静默的。

我的做法：

1. 每次改完 `lib/*.js`，复制一份到「快照目录」
2. 写一个 `hash.json`：`{ "文件名": { "patched": "sha256", "base": "sha256" } }`
3. 计划任务每 5 分钟跑一次守护：算 live 文件的哈希
   - 等于 `patched` → 正常
   - 等于 `base`（被升级覆盖了）→ **用快照盖回去**
   - 两个都不等 → 只报警，不动手（可能是你正在改）
4. 恢复脚本留一份手动兜底

**为什么不直接 `git checkout` 或者阻塞升级**：升级带来的新能力你也想要；守护的思路是「升级可以发生，但我的补丁要能自动回来」，而不是「锁死版本」。

## 6. 加面板（可选）

一个本地 HTTP 路由 + 设置页，浏览器里看和调：

- 养成数值、激素、身体状态
- 日记最近 7 天、用量（请求数 / 缓存命中 / 日均花费）
- 服务状态红绿灯（WS 通不通、侧车活没活、守护跑没跑）
- 场景开关（只对主人开放）

**为什么面板值得做**：调数值不需要每次都去翻 JSON；更重要的是「能看到状态」，你才判断得出她说的话是设定还是 bug。接口/页面怎么写见 [`面板/README.md`](../面板/README.md)。

注意：DSH Web 的设置页接口需要桌面端登录态，命令行直接 curl 会 **401**，那是正常的。

## 7. 会话清理（长期挂着必备）

QQ 会话日志会一直长，几个月就是几个 G。做法见 `03`：
按「目录里最新文件 mtime 超过 N 小时 + 不是当前挂着的会话 + 保留每个聊天最后一条」三条同时满足才删，删完顺手清掉对应的投影缓存。

**为什么一定要「保留最后一条」**：否则你删掉的可能是正在用的上下文，下次唤醒她会像失忆——而你以为是模型抽风。

---

## 8. 每次改动后的验证清单

- [ ] 日志有 `bridge ready`
- [ ] 私聊回一句、群里 @ 回一句（不 @ 不回是设计）
- [ ] 工具数量对得上（插件注册了多少个）
- [ ] 侧车只有一个进程
- [ ] 状态文件是预期的开/关
- [ ] `harness.log` 里没有 `agent create failed`
- [ ] 面板「状态」页全绿（或知道为什么黄/红）
