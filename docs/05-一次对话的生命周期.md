# 05 · 一次对话的生命周期

从「你在 QQ 里敲下一句话」到「她回你」，中间发生了什么。
以 `dsh-onebot-qq@0.9.4` 为例；函数名是稳定的，行号会随版本漂移，所以只写函数名。

---

## 总览（六个阶段）

```
①  收到         NapCat ──WS──▶ 插件 onEvent
②  过滤         是不是叫我？是不是黑名单？是不是我自己？
③  拼装         inbound.js：把一堆资料拼成一条 user message
④  推理         宿主把 system + user 发给模型；模型回文本 / 调工具
⑤  发送         interim / outbound：分条、延迟、失败重试
⑥  旁听         侧车 onEvent：算数值、写状态；10 分钟 tick 一次
```

---

## ① 收到：WS 上的一个事件

NapCat 把 QQ 的消息事件通过 WS 推过来，插件在 `connection.js` 里接，交给 `inbound.js`。

事件基本长这样（简化）：

```json
{ "post_type": "message", "message_type": "group",
  "group_id": 123456, "user_id": 1000000001,
  "sender": { "nickname": "某某", "card": "" },
  "raw_message": "@机器人 你好", "message_id": 42, "time": 1700000000 }
```

**为什么从事件开始讲**：所有「她怎么突然说话了」的谜题，最后都回到「有没有这个事件」。
先确认事件到了，再谈她为什么说错话。

---

## ② 过滤：谁有资格唤醒她

在 `inbound.js` 的入口做几件事，顺序很重要：

1. 自己的消息 → 直接丢（否则她会跟自己聊起来）
2. 私聊：`dmPolicy` / `dmFriendsOnly` 名单校验
3. 群聊：`requireMention`（@ 或叫名字）才继续；`restrictedMembers` 可以单独限权
4. 限流 / 冷却（同一人刷屏不该每次都唤醒）
5. 写审计日志（谁触发的、被怎么处理）

**为什么把这些放在最前面**：它们决定「花不花这次钱」。放到后面就等于「先花钱再判断该不该花」。

---

## ③ 拼装：一条消息其实是十块拼图

`inbound.js` 把下面这些**字符串拼接**成最终发给模型的 user message：

| 顺序 | 块 | 内容 | 为什么在这 |
|---|---|---|---|
| 1 | 群前缀 | `[群 123456 某某]` | 让模型知道「在群里、谁在说」 |
| 2 | `<context_note>` | 这个会话最近 N 条聊天记录 | 提供现场感；太长会淹后面 |
| 3 | `[安全边界]` | 说话人是谁、能做什么、不能做什么 | 先立规矩 |
| 4 | `<persona>` | 人设**尾部**（每回合补的性格骨架） | 贴脸 |
| 5 | `<closet>` / `<kinship>` / `<anger>` / `<uncanny>` / `<egg>` | 当前状态（穿着、对方户籍、怒气、模式、彩蛋） | 状态影响怎么说 |
| 6 | `<user_message>` | 你的原话 | 最近处 = 最认真读 |

**几个真实教训**：

- **状态块要「有才注入」**：没人登记户籍，`<kinship>` 就是一个空字符串——不占一个 token。
- **触发型提示要放最后**：我试过把「必须贴出这段文本」插在最前面，前面还有十几 K 聊天记录，她直接无视；挪到原话后面立刻生效。
- **后缀比前缀贵**：都在 user message 里，但越靠后越不容易被忽略；所以「重要的短提示」放后面，「背景资料」放前面。

---

## ④ 推理：系统提示 + 工具

宿主拿到两条消息：

```
system:  你的身份（宿主规则）+ ## 角色人设（常驻） ← 人设**核心段**在这里
user:    上面拼出来的那一大坨
```

系统提示是**会话创建时注入一次**的，之后每轮都相同 → 吃缓存价。
这就是为什么要分层（见 02）。

模型回合里可能发生三种事：

1. 只输出文本 → 直接发
2. 输出文本 + 调工具 → 工具结果回到模型，再来一轮
3. 只调工具 → 继续

工具在 `tools.js` 里注册（`registerTools(ctx, bridge, connection, limits)`），
注意 `bridge` 是「发消息的能力」，`connection` 是「OneBot 动作的能力」——
**调错了就会得到 `xxx is not a function`**，这是我最常犯的错之一。

---

## ⑤ 发送：为什么她的回复是好几条

`outbound.js`：

- 长回复按句切，目标每段约 42 字，最多 6 段
- 段间随机 180~520ms 延迟（太整齐像机器）
- 单条发送失败 → 等 400ms 重试一次 → 两次都失败才抛错并写审计
- **不重试的后果**：静默丢消息。你以为是模型没说话，其实是没发出去

`interim.js` 处理「一个回合里说了好几段」的情况：

- 中间那段（还没说完就调工具）先发出去，让对面知道「在想」
- 结束时用一段总结替换掉中间记录（`recall` 撤回）
- **坑**：如果总结发送失败，就别撤回中间记录，否则那段话彻底消失

**为什么值得做**：一次几十秒的等待，中间没有任何反馈，体感像掉线。
分条 + 中间态是「像人」的关键细节——但它也是 bug 高发区。

---

## ⑥ 旁听：0 token 的那一半

侧车连同一个 WS，只订阅、不发言。收到事件后：

```
onEvent(msg)
  ├─ 更新印象/好感（谁在说话、说了多少、语气如何）
  ├─ 更新激素（被叫到 / 聊得暖 / 被怼 → 加减）
  ├─ 检测特殊状态（怒气触发词、模式唤醒动作……）
  └─ 需要时 → 写状态文件
每 10 分钟 tick()
  ├─ 推进养成数值（饿、困、体力、体重……）
  ├─ 到点判定（睡/醒、每日重置）
  ├─ 状态卡写盘（供插件下回合注入）
  └─ 主动行为判定（要不要找人说话）
```

**为什么单独一个进程**：
1. 它不需要模型，塞进插件只是白占宿主资源；
2. 能独立重启，改完立刻生效；
3. 崩了不影响对话。

**为什么要「重读磁盘」**：工具也会写同一个 JSON，内存里的快照可能是旧的。
每次 tick 先读盘、比较 `updatedAt`，磁盘新就采纳——这是两个写者共存的唯一低摩擦方案。

## 一张排查表

| 症状 | 先看哪一步 |
|---|---|
| 完全没反应 | ① 事件到了吗？② 过滤是不是把她自己拦了？ |
| 回复很短/很怪 | ③ 拼装内容对不对？状态块是不是空/错 |
| 该调工具没调 | ④ 工具注册成功了吗？参数 schema 对不对 |
| 回复丢了一半 | ⑤ 分条/重试/撤回逻辑 |
| 数值不动 | ⑥ 侧车活着吗？tick 在跑吗？字段名对吗 |
| 隔一天像失忆 | 轮换交接 / 会话清理 |

**用法**：从上往下走，每步只看一个信号（日志/文件），别跳。
