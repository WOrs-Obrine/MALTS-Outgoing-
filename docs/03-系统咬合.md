# 03 · 系统咬合：谁写、谁读、哪里会互相踩

这一份讲的是「零件之间怎么咬住」。装的时候看不出来，改的时候全是它。

---

## 1. 三类数据，别混

| 类别 | 谁产生 | 谁消费 | 例子 |
|---|---|---|---|
| **人设** | 你手写 | 插件每回合读 | 人设 md、语料 md |
| **状态** | 侧车算、工具写 | 插件拼进消息、面板展示 | 养成数值、心情、身体、当前场景 |
| **记忆/语料** | 侧车写摘要、你写原料 | 模型按需 `read` | 印象摘要、日记、地标、人物卡 |

**为什么要分**：人设是「她是谁」，状态是「她此刻怎样」，记忆是「她记得什么」。
三者混在一起写进人设文件，会得到一个「每天都一样、又经常自相矛盾」的人。

---

## 2. 咬合点 A：注入的拼装顺序

一条 user message 在插件里是**拼**出来的，顺序大致：

```
<context_note>  最近聊天记录（谁说了什么）
[安全边界]      说话人是谁、能做什么
<persona>       人设尾部（每回合补的那一小段）
<状态块>        穿着 / 心情 / 身体 / 场景
<user_message>  你的原话
```

**教训一：越长的东西越容易被忽略。** 我把一个触发提示插在整条消息**最前面**（前面还有十几 K 的聊天记录），结果她根本没照做；改成**追加到末尾**、紧跟原话之后，立刻生效。
**模型是在读一段文字的「最近处」最认真**——这是注意力，不是玄学。

**教训二：拼装顺序 = 优先级。** 安全边界要排在前面（先立规矩），当前场景和状态要靠近原话（最后决定怎么说）。
两者冲突时，通常「靠近原话的」赢。

---

## 3. 咬合点 B：字段契约（最阴的一类 bug）

侧车写 `激素.json` 的 `anger`，插件读 `激素.json` 的 `anger`，面板也读它——
**三个地方各写各的字段名，只要有一处拼错，症状是「数字永远是 0」，而且不报错。**

真实案例：

- 面板读 `stats.pressure`，工具写 `statsBy[qq].pressure` → 面板永远 0，看起来「机制没工作」，其实机制一直在跑，只是没人看见。
- 换装改成按人存 `outfitBy[qq]` 之后，旧的「全局 outfit」还被某个函数写 → 两个人互相串衣服。

**规矩**：
1. 一个状态，只有一个**权威字段**；其余都是派生（能算出来的别再存一份）。
2. 写字段的人和读字段的人**必须改同一个常量**（比如都从 `DEFAULT()` 里取初始结构，别各写一遍字面量）。
3. 加字段时三处一起加：默认值、写入、读取；漏了默认值就会得到 `undefined` 而不是 0。

---

## 4. 咬合点 C：两个进程同时写一个 JSON

侧车每 10 分钟 tick 一次写盘；agent 的工具（改数值、换衣）也会写盘。两边都在跑。

**我的做法**：

- 侧车 tick 开始时**重读磁盘**，如果磁盘比内存新 → 用磁盘覆盖内存（日志「采纳后台改的养成数据」），再算增量、再写。
- 工具写完立刻落盘，并且**只改它该改的字段**（深合并，不整份覆盖）。
- 侧车在 `saveGrowth` 时对「别人的字段」只带过去、不覆盖（例如换装表：只读磁盘的 `outfitBy` 进来，不用内存的旧值盖它）。

**为什么不用文件锁**：Windows 上文件锁很难写对，而且卡住一次就是整条链路停摆。
「读最新 → 算 → 合并写」的代价是偶尔丢一次增量，但对这种低频、非金融的数据，完全够用。

---

## 5. 咬合点 D：系统提示是「每个会话一次」

人设核心段注册在 agent 的 system prompt 里（`systemPrompt.section({ name: 'channel:persona', order: 85 })`）。
它**在该会话创建时注入一次**，之后靠缓存省 。

后果：

- 改人设尾部（每回合拼的那段）→ **下一条消息就生效**。
- 改人设核心（系统提示那段）→ **当前会话不生效**，要 `/new` 开新会话（或者等自动轮换）。
- 换人设（`绑定.json` 指到另一份）→ 旧会话会检测到「系统提示里的人设名和现在不一致」，退化成整段注入（贵但不丢人设），新会话才吃缓存。

**所以设计上要「宽容」**：读不到、对不上，就退回「整段塞进消息」的老办法，而不是直接不注入。
功能优先，省钱的路径可以少走。

---

## 6. 咬合点 E：轮换与交接

上下文会一直长，长到一定程度必须换一个新会话。插件里三个阈值任一触发就换：

```yaml
autoRotateTurns: 50          # 回合数
autoRotateCtxTokens: 110000  # 上下文 token（要低于模型窗口，留 15~20% 余量）
autoRotateHours: 24          # 兜底：一天必换，防漂移
handoffLines: 60             # 交接写多少条最近记录
```

换会话时写一份交接（谁在聊、聊到哪、答应过什么），写到「近期对话」目录，**只写指针不写全文**。
新会话的开场会读到它，于是「记得刚才」。

**成本视角**：每换一次会话，第一条消息要重新读一遍系统提示 = 一次冷启动（几万 token 的未命中）。
所以阈值不是越小越好：30 回合换一次，比 50 回合多付 60% 的冷启动钱。

---

## 7. 咬合点 F：面板只读，写入走 API

面板直接读同一批 JSON（养成/激素/身体/印象），**但不直接写文件**——所有修改走 HTTP 路由（保存设置、改人设指针、切场景开关）。

**为什么**：
1. 面板是浏览器里跑的，直接写文件等于把「文件格式」复制到第二处，两边容易漂；
2. 走 API 就能在一处做校验（类型、范围、权限）；
3. 出问题能看日志。

例外：面板里那些「展示用」的东西（比如世界书条目、语料索引）只读不写，永远由文件本身决定。

## 8. 咬合点 G：补丁与守护

| 目录 | 作用 |
|---|---|
| `node_modules/<插件>/lib/*.js` | 真正在跑的文件 |
| `快照\` | 我改完的副本 |
| `hash.json` | `{ 文件名: {patched, base} }` |
| `last-run.txt` | 守护最近一次结果 |

守护每 5 分钟：算 live 哈希 → 等于 `patched` 正常 / 等于 `base` 说明被升级覆盖 → 用快照盖回 / 都不等 → 只报警。

**注意 `hash.json` 可能带 BOM**：`JSON.parse` 会死在第一个字符上，读之前先 `replace(/^\uFEFF/, '')`。

## 9. 记忆三层

| 层 | 位置 | 谁写 | 何时读 |
|---|---|---|---|
| 热 | 当前状态卡 / 私聊-<QQ>.md | 侧车 / 轮换时 | 每回合自动注入 |
| 温 | 人物.md、约定.md、日记/ | 侧车 + 工具 | 聊到具体人或旧约定时 `read` |
| 冷 | 工程台账、事故记录 | 人 | 出问题时翻 |

**别把三层合成一个大文件**：热记忆每回合都进上下文，一个字都是钱；温记忆读一次就是几千 token；冷记忆只在排查时用。
混在一起的后果是——她每回合都在读一本她根本不需要的书。

## 10. 踩坑速查

| 现象 | 原因 | 解法 |
|---|---|---|
| 明明写了规则却不照做 | 提示插在超长消息最前面 | 挪到原话后面 |
| 机制「没工作」 | 读的字段名和写的不同 | 统一默认值来源 |
| 两个人互相串状态 | 还有地方在写全局兜底 | 全部改成按人存，删掉镜像 |
| 改人设没反应 | 改的是核心段（系统提示） | 发 `/new` 或改尾部 |
| 升级后行为变了 | 插件被覆盖，补丁丢了 | 守护盖回 + 改完立刻存快照 |
| 她「忘了刚才」 | 会话被清理/轮换，交接没读到 | 检查近期对话目录 |
