# 04 · 踩过的坑：现象 → 根因 → 修法

每条都是真事。按主题排，每条结尾一句「教训」——那句才是我真正学会的东西。

---

## 一、补丁与升级

### 1. 改好的代码几分钟后自己变回旧版（最阴）

**现象**：明明改好了，过一会儿行为又变回去；日志里没有任何报错。
**根因**：守护脚本每 5 分钟比对文件哈希，而 `hash.json` 里的 `patched` 是几天前的旧值 → 它认为「文件被改坏了」→ 拿快照盖回去。
**修法**：哈希表只用来判断「有没有被重装回原版」——`当前哈希 === base` 才盖快照，其余只记 `unknown` 并报警。改完代码要**同时**更新快照和 `hash.json`。
**教训**：任何「自动恢复」机制，都必须先区分「被破坏」和「被人改」。

### 2. 插件代码不热加载

**现象**：改了 `lib/*.js`，重启侧车、刷新面板都没用。
**根因**：插件在宿主启动时加载一次，配置也是启动时读。
**修法**：改插件代码或配置 → **完全退出并重开宿主**（不是关窗口），然后看日志有没有 `bridge ready`。人设 md / 语料 md 是例外（每回合现读，即时生效）。
**教训**：把「经常要改的东西」做成数据，把「很少改的东西」做成代码。

### 3. 工具少写一个 `output` 字段 → 整个群哑掉

**现象**：群消息能被叫到，紧跟着 `agent create failed (Cannot read properties of undefined (reading 'render'))`，然后一个字都发不出；私聊老会话反而正常。
**根因**：某个工具注册时缺 `output: { schema, render }`，注册阶段抛错，这个群的 agent 建不起来。
**修法**：每个工具都给 `output`；改完用「缺字段就 throw」的离线 shim 跑一遍注册函数，提前抓到。

### 4. 插件升级把补丁冲没了

**现象**：重启报一个 schema 相关的 TypeError → 启动失败 → 桌面端自动恢复机制把插件**升级到上游新版** → 我的补丁全失效。
**修法**：数值用 `.step(1)` 而不是不存在的 `.int()`；把插件**钉死版本**（junction 指向固定生成目录）；升级前备份 `lib/`，升级后逐条重打。
**教训**：补丁不是「改一次就完」，是一次性的、会被擦掉的涂鸦。要么接受维护成本，要么把改动做成插件外的扩展。

## 二、成本

### 5. 一天十几块，账单像在烧钱

**现象**：没聊几句，一天 ¥6~7，甚至更多。
**根因**：每回合把「人设全文 + 一堆资料」塞进 user message。这部分每轮都变，按**未命中价**算（¥1/百万），比缓存命中贵 50 倍。
**修法**：拆成「系统提示（一次）+ 每回合小尾巴（几 K 字）」；语料改成按需 `read`。
**教训**：先把「每回合都发什么」列出来，再谈优化。

### 6. 把轮换阈值调小，反而更贵

**现象**：轮换从 40 回合砍到 30，账单没降。
**根因**：每换一次会话，第一条消息要重读一遍系统提示 = 一次冷启动。阈值太小，冷启动次数翻倍。
**修法**：阈值往上调（我最后是 50 回合 / 110K token），把冷启动摊薄。
**教训**：省钱的指标不是「单次多便宜」，是「一天总账」。

### 7. 统计脚本算出来的钱是假的

**现象**：面板说今天 ¥29，实际只有 ¥5。
**根因**：会话轮换/恢复会把历史事件重写进新文件，同一请求被算好几遍。
**修法**：全局按「(秒级时间, miss, hit, out)」去重，别按会话去重；日期归属要有合理窗口（否则几十天前的历史会被算进今天）。
**教训**：统计脚本先和官方账单对一次账，对不上就是口径错了。

## 三、进程与服务

### 8. 侧车跑了两个实例，状态互相覆盖

**现象**：数值一会儿涨一会儿掉，像有人在同时改。
**根因**：手动重启和看门狗同时拉起，各写各的 JSON。
**修法**：启动前先查实例数（按命令行匹配，排除 `runner.js` 之类）；先杀后起；日志里打印 PID。

### 9. 杀进程把自己的终端一起杀了

**现象**：一条 kill 命令下去，自己的后台任务也死了，报一个莫名其妙的退出码。
**根因**：自己的命令行里也含匹配关键字。
**修法**：排除自己的解释器；或把关键字在脚本里拼接（命令文本里不出现完整字面量）；或写成 `.cmd` 文件去调用。
**教训**：按名字杀进程前，先把命中列表打出来看一眼。

### 10. 按 `node.exe` 找不到侧车

**根因**：它是被桌面程序以子进程方式拉起的，映像名就是那个程序，不是 node。
**修法**：查命令行而不是映像名；统计时两者都比。

### 11. 改了 mjs，运行中的服务没变

**根因**：ESM 模块在进程启动时就缓存了。
**修法**：改完重启那个进程。宿主里跑的东西要重开宿主。

## 四、数据与文件

### 12. 「我改了，但对方读到的还是旧的」

**现象**：两个路径同名文件、内容不一样。
**根因**：用「原子写」方式替换文件（编辑器保存、某些脚本）会**断开硬链接**——新文件是新 inode，另一侧路径还指着旧 inode。
**修法**：改共用文件时**原地写**；或者改完删掉另一侧、`mklink /H` 重建，再用 `fsutil file queryfileid` 对 inode。

### 13. 两个进程写同一份 JSON，字段互相覆盖

**现象**：刚改的数值过一会儿自己变回去。
**根因**：A 内存里是旧快照，整份写盘，把 B 的新值盖了。
**修法**：写之前重读磁盘，磁盘更新就采纳磁盘；写入深合并、只改自己负责的字段。
**教训**：文件锁很难写对，「读最新 + 合并写」更稳。

### 14. 中文 `.ps1` 解析炸

**现象**：`表达式或语句中包含意外的标记`，但 `ParseFile` 有时报 0 错。
**根因**：文件是 UTF-8 **无 BOM**，Windows PowerShell 5.1 按 ANSI 解析中文注释，把结构搞乱。
**修法**：含中文的 `.ps1` 一律存 **UTF-8 带 BOM + CRLF**；改完重新转一次（编辑器保存常常又变回无 BOM）。

### 15. JSON 带 BOM

**现象**：`JSON.parse` 报 `Unexpected token '\uFEFF'`。
**修法**：读之前 `text.replace(/^\uFEFF/, '')`，写回时不要 BOM。

### 16. Windows 文件锁

**现象**：`EPERM: operation not permitted, rename`。
**根因**：目标文件被杀软/索引/别的进程占用。
**修法**：写到临时目录再复制；或重试几次。做实验时干脆换到 `%TEMP%`。

### 17. 时间戳时区不一致，健康检查误报红

**现象**：日志明明刚跑过，面板说「3 小时没跑」。
**根因**：写日志用 UTC（`toISOString`），读的时候按本地 +08:00 解析，差 8 小时。
**修法**：**新鲜度看文件 mtime，不看日志里的时间字符串**。

## 五、上下文与记忆

### 18. 规则明明写了，她不照做

**现象**：人设里写着「动作少写」，她还是写一堆。
**根因**：① 规则在长尾里，根本没注入；② 规则在超长消息的最前面，被淹；③ 和另一条规则冲突。
**修法**：规则放核心或尾部；触发型提示放在**原话后面**；冲突的两条删掉一条。
**教训**：模型对「离原话最近的内容」最认真。

### 19. 她显得「记性很差」

**现象**：刚聊过的事，换个会话就不知道。
**根因**：会话轮换了但交接没写/没读到；或旧会话被清理脚本删了（删之前没保留最后一轮）。
**修法**：轮换时写交接（指针式）；清理脚本必须「保留每个聊天最后一条」。

### 20. 语料塞太多，开始复读 / 串味

**根因**：多份语料同时注入，模型分不清「现在该用哪份」。
**修法**：一次只 `read` 一节；语料里写清适用场景；触发型内容做成「命中才注入」。

### 21. 概率型触发不受控

**现象**：说「偶尔发生」，结果一天三次，或者一周不出现。
**根因**：每条消息掷骰子 → 消息越多越频繁，而且不可复现。
**修法**：改成**攒值**：时间慢涨 + 特定事件加值 + 阈值触发 + 冷却。可调、可看、可解释。
**教训**：凡是「随机」，都要先问一句「我能不能把它变成可解释的」。

### 22. 面板某条永远是 0

**根因**：读的字段名和写的字段名不是同一个。
**修法**：写个最小脚本打印真实 JSON，比对字段；统一默认值来源。

## 六、面板与接口

### 23. 命令行请求面板接口全是 401

**根因**：面板挂在宿主 Web 端口下，需要桌面端登录态。
**修法**：正常现象。验证用浏览器，或用 standalone 脚本复刻同样的读文件逻辑。

### 24. 面板改了没生效

**根因**：面板是打包产物，宿主不重开就不会重新打包。
**修法**：完全退出并重开宿主。纯数据改动的刷新即可。

## 七、一条元教训

**一次只改一样，改完立刻验证。**

我吃过最多的亏，不是某个坑本身，而是「一次改五处 → 出问题 → 不知道是哪一处」。

最小验证清单：

1. `node --check`（语法）
2. 直接调用目标函数跑一遍（逻辑）
3. 看日志有没有新 error（运行）
4. 让真人发一条消息看输出（端到端）
